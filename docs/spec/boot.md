# 起動と配布

[仕様の目次](README.md)

Binette を「カーネルだけ配り、残りは取ってきてブラウザの中に置いて動かす」形にするための仕様です。目的は、アプリの上でアプリを作れること、ホームバーのような OS の部品もアプリの上でいじれることです（のぞみ 2026-11-01）。

> [!NOTE]
> 2026-11-01 に決めた構成です。目録とファイルの木からの起動、カーネルの分離配布、Service Worker、役割の割り当てと辞書 API、設定アプリの更新は実装済みです。常駐 Cadre とアプリ表示領域も実装済みです。ファイル名・パス・関数名は、どれも **案** です。役割と API の受け渡しは [roles.md](roles.md) にあります。

## 方針（決定 2026-11-01）

- カーネルは 1 つか数個のファイルにして配る
- ほかの部品（Cadre、システムアプリ、AS のコンパイラなど）は HTTP で取ってきて、ブラウザの中のファイルの木に置いて動かす
- 配布元から取る、変えない側のもの（固定物）は、WASM か minify した JS にして、ハッシュで改変を検知する
- カーネルは、まず TS（今の Régie の延長）で作る。形が固まってから、中身を Rust（ビルド済みの WASM）に移すかを決める。アプリの上で編集してビルドし直すもの（Cadre やアプリ）は、ブラウザで動く asc を使うので AS のまま

## 層（決定 2026-11-01）

| 層 | 中身 | 変えられるか |
| --- | --- | --- |
| 入口 | `index.html`、Service Worker | 変えられない |
| カーネル | Régie と Scene。起動、取得、検査、ファイルの木、Worker ＋ WASM の実行、ライフサイクル、スタック、役割の割り当て、権限、アプリの UI の描画、Cadre が落ち続けたときの最低限の大枠、Apps、復旧画面 | 変えられない |
| ファイルの木 | パス → 中身。`/system` の上に `/user` を重ねて見せる | 権限のあるアプリだけ |
| ユーザー空間 | Cadre（ホームバー・通知などの大枠）、ホーム、設定、デザイナー、ふつうのアプリ。どれも役割を持つかどうかだけが違う、ふつうのアプリ（[roles.md](roles.md)） | 設定アプリ以外は差し替えられる |

- Scene はアプリの UI を DOM に描くので、メインスレッドで動く。取ってきたコードをメインスレッドで動かさないため、Scene はカーネルに入れる
- アプリ（システムの部品を含む）は、どれも Worker の中の WASM で動き、DOM には触れない

## 配るファイル（案）

| ファイル | 仕事 |
| --- | --- |
| `index.html` | 入口。`regie.js` を SRI（`integrity` 属性）付きで読む |
| `regie.js` | カーネル本体。minify した JS |
| `regie-worker.js` | アプリを動かす Worker の中身 |
| `build-worker.js` | asc を動かすビルド専用 Worker の中身（案） |
| `sw.js` | Service Worker。入口とカーネルをキャッシュし、ファイルの木を URL で返す |

- カーネルは `regie.js` と `regie-worker.js` の 2 つにする（決定）。ビルド用の入口は別の `build-worker.js` にする（案）。Worker の中身は別ファイルにする（今の Blob URL の Worker をやめる。CSP の `worker-src blob:` も要らなくなる）
- `manifest.webmanifest` と `icon.svg` も入口に置く。配布元の目録と固定物は同じ配布先から別に取る
- AS のコンパイラ（asc）はカーネルに入れない（決定）。重い（約 13.6 MB、gzip で約 2.9 MB）ので、ファイルの木から取る部品にする

## 取ってくるファイル（案）

| パス | 仕事 |
| --- | --- |
| `manifest.json` | 目録。版と、各ファイルのパス・SHA-256・大きさ |
| `system/boot.json` | 役割の既定の割り当てと既定の提供リスト（`lists`、ローカルは既定で空配列） |
| `system/apps/<アプリ>/` | システムアプリ。既定は `cadre/` だけで、ホーム・設定をサブアプリとして含む。`app.json` とビルド済みの `.wasm` |
| `system/bundled/<アプリ>/` | 同梱アプリ。システムアプリと同じファイル形式（案） |
| `system/tools/asc.js` | AS のコンパイラ。依存込みの minify した JS で、Worker の中で動かす |
| `system/libraries/replique/` | ブラウザでのビルドに渡す Réplique の `index.ts`、各機能の `.ts`、機能名からパッケージ版への辞書 `index.json`（決定） |

## ファイルの木（決定 2026-11-01）

- できることは、パス・読む・書く・一覧・削除・重ね合わせだけ。POSIX のような権限の欄やリンクは持たない
- 保存先は中身が OPFS、メタデータが IndexedDB（[storage.md](storage.md)）。`/system`・`/user` は Binette 自身の 2 つの層として扱う
- 見え方は、`/system` の上に `/user` を重ねたもの。同じパスなら `/user` が勝つ。`/user` のファイルを消せば元に戻る
- アプリはファイルの木に、辞書の API（[roles.md](roles.md)）でしか触れない。権限のないアプリは読むことも書くこともできない（決定）
- 設定アプリはコアで、設定を含む `/apps/cadre` パッケージは `/user` で上書きできない（決定。[roles.md](roles.md#設定アプリ決定)）

| パス（案） | 中身 |
| --- | --- |
| `/system/…` | 配布元から取ったもの。読み取り専用。更新で丸ごと入れ替える |
| `/user/…` | 編集した分だけ |
| アプリの `/source/…`・`/build/…` | インストールしたアプリのソースとビルド結果 |
| アプリの `/data/…` | アプリごとのデータ。将来、Coulisses へのバックアップの対象 |

- `AppStore`・`SystemStore` はファイルの木の上に保存する（API と保存先の細部は案。[regie/store.md](regie/store.md)）。目録とハッシュの検査は実装済み。アプリに渡す権限付き API のうち、アプリごとのデータ（`storage`）は実装済みで、ファイルの木そのもの（`fs`）はまだ実装していない

## 目録と現在の配布（案）

`manifest.json` の形と名前は案です。`version` はファイル一覧の内容を比べるハッシュ、`label` は人が読む版、`kernel` は組になる Service Worker のカーネルの印です。`files` は各ファイルのパス、SHA-256（小文字の 16 進）と大きさ（バイト数）を持ちます。古い、`label` と `kernel` がない目録も読みます。保存した目録は `/system/.manifest.json` に置き、固定物と一緒に入れ替えます。

```json
{
  "version": "ファイル一覧のハッシュ",
  "label": "0.1.0+1234abcd",
  "kernel": "binette-v0.2.0-4-1234567890abcdef",
  "files": [{ "path": "system/boot.json", "sha256": "ファイルの SHA-256", "size": 123 }]
}
```

`system/boot.json` は `roles.cadre`・`roles.home`・`roles.settings` に既定アプリの ID を入れます。ローカルで `BINETTE_LISTS` を指定しない場合の出力は次のとおりです。GitHub Pages ではブランチの Binette の提供リスト、`https://nozomi-hiragi.github.io/binette-apps/` の順で `lists` に書きます（[app-manager.md](app-manager.md#binette-の既定の提供リスト)）。ローカルでも `BINETTE_LISTS` にカンマ区切りの https の URL を渡すと指定できます。

```json
{
  "roles": { "cadre": "cadre", "home": "cadre.home", "settings": "cadre.settings" },
  "lists": []
}
```

カーネルはこれを役割の初回の割り当て（`SystemOptions.roles`）にし、そのあとの割り当ては設定が決めます（[roles.md](roles.md#役割の割り当て実装済み形は案)）。`system/apps/<フォルダ>/` と `system/bundled/<フォルダ>/` に `app.json`、`app.wasm`、`index.html`、必要な `icon.svg`・サブアプリの `sub-icons/<番号>.svg` を置きます。サブアイコンのパスは配布時に書き換え、目録にも含めます。同梱アプリの配置と入手元は案です。既定の Cadre は `apps/cadre` です。ホーム・設定も同じパッケージとビルド結果を使い、個別の配布フォルダは持ちません。同梱の Filer の ID は `filer` です。デザイナーは binette-apps の提供リストから入れます。

## アプリの置き方（決定 2026-11-01）

- インストールしたアプリは、ソース（`app.json`、`.ts`、`.css`）をそのまま置き、ブラウザでビルドして、結果を同じ所に残す。アプリの上でアプリを作るときと同じ道にする
- ビルドは Worker の中の asc で行う
- システムアプリは固定物なので、ビルド済みの `.wasm` を取ってきて置く。ブラウザではビルドし直さない

ブラウザ向けビルドの API と保存先は案です。asc と Réplique は保存済み目録の SHA-256 と大きさを検証してから使います。Réplique はビルドに AS ソースが必要なため、この配布物は JS や WASM ではなくソースのままです。

## 起動の流れ（決定 2026-11-01）

1. `index.html` が `regie.js` を読む。改ざんはブラウザが SRI で検知する
2. カーネルがファイルの木を開く
3. 本番では保存済み目録のカーネルの印と動いているカーネルを、開発時は保存済み目録の版と入口に埋め込んだ版を照合する。組が合わないときは合う `/system` を取得し、取得できなければ復旧画面を出す
4. 初回は目録と固定物を取り、SHA-256 を検査して `/system` に置く。保存済みの組が使えるときは、それで起動しながら更新を確認する
5. `boot.json` と設定から役割の割り当てを決め、カーネルは Cadre だけを起動する。Cadre が大枠とアプリの表示領域を描き、その中でホームを呼ぶ（[roles.md](roles.md)）
6. `/system` のファイルは、読み込むたびにもハッシュを確かめてから動かす
7. どこかで失敗したら、カーネルだけで描く復旧画面を出す

初回は、既定のアプリを割り当て済みで出します（決定）。

### 開発時と本番の組の識別（決定 2026-11-11）

- 本番はビルドで入口の `binette-kernel`、Service Worker、目録の `kernel` に同じ印を付ける。保存済みの組が合っていれば、新しい配布物があっても起動時には入れ替えない。準備した更新と待機中の Service Worker は、設定から適用するまで維持する
- 開発時は `build:system` が作った目録の `version`（固定物のパス・SHA-256・大きさから作る内容ハッシュ）を、Vite が入口を返すたびに `binette-dev-system` に埋め込む。本番のカーネルの印とは混ぜず、保存済み目録の `version` と照合する。再ビルド後の再読み込みでは新しい版を照合する
- 開発時に保存済みの版が違う場合は、入口と一致する目録だけを使い、既存と同じ経路で固定物の大きさと SHA-256 を検証してから `/system` を置き換える。一致する保存物はオフラインでも検証して起動できる。一致する配布物を取得できない場合、検証に失敗した場合、入口の開発用の版がない場合は復旧画面に進む。生成目録がない、または版が不正な場合は、開発サーバーは入口の生成を失敗させる
- システム・同梱のビルド済みアプリで ABI が合わない場合は、復旧画面の「/system を取り直す」を案内する。提供リストのアプリには従来どおりアプリの管理からの入れ直しを案内する

## 更新（決定 2026-11-02）

- スケジューラの OS の予定 `os/update`（初期値 30 分、[scheduler.md](scheduler.md#os-の予定)）と、設定の「今すぐ確認」で目録を確かめる。目録の取得と比較は 8 秒で時間切れとし、失敗は設定の行に知らせる
- 新しい組が見つかったら差分を裏で取得し、SHA-256 を検査して別の置き場に準備する。先取りには目録確認の 8 秒制限を掛けず、進行中と失敗を設定の行に知らせる。失敗したら再試行できる
- 設定の「更新」は準備済みの `/system` と対応する待機中の Service Worker を切り替え、再読み込みする。片方だけ変わった場合も同じ操作で更新する。準備の置き場はメモリ上で、再読み込み後は改めて準備する（形は案）
- 起動時に配布元を取得できなくても、保存済みの目録と固定物を検証し、動いているカーネルと組が合えば起動する。組が合わず、合う配布物も取得できなければ復旧画面を出す
- 取得元は今は同じオリジンだけ。設定から復旧画面を開ける

## 改変の検知（決定 2026-11-01）

- カーネル: `index.html` の SRI でブラウザが確かめる（カーネルは自分のハッシュを自分では確かめられないため）
- `regie-worker.js` と `build-worker.js` は Worker に SRI を指定できないため、現在は同じオリジンと HTTPS を信頼する。改変の検知方法は未決。案として、`regie.js` に期待するハッシュを埋め込み、信頼できる Service Worker が Worker への応答をその値で検証してから返す方法がある。初回も SW の制御が始まってから Worker を起動し、SW とハッシュ伝達の信頼方法、更新時の版の整合を決める必要がある。別途 fetch して検証するだけでは Worker の取得時に内容が変わる可能性を防げないため、採用しない
- `/system` のファイル: 目録の SHA-256 と、取ったときと読み込むたびの両方で比べる。保存された中身を書き換えられても気づける
- 目録: 今は HTTPS と同じオリジンを信じる。取得元を増やすときに、署名とカーネルに埋め込む公開鍵を足す
- 現在の保存目録は署名がない。オフライン時や更新待ちの旧版など、同じ版の配布元目録と照合できない場合は、保存目録と固定物の両方を同時に改変されると検知できない。旧版の目録の信頼方法は未決
- `/user` と `/apps` のファイルはハッシュで見ない。書けるのは権限のあるアプリだけなので、権限で守る

## Service Worker（決定 2026-11-01）

- 入口とカーネルをキャッシュし、オフラインでも起動できるようにする
- 新しい Service Worker は待機し、準備済みの `/system` と組を確かめたうえでページからの合図を受けて有効になる。初回はすぐに有効にできる
- ファイルの木を URL として返す（例 `./fs/system/…`、パスは案）。画像や CSS などがふつうの URL で読め、相対パスもそのまま使える
- `./fs/` は IndexedDB の表と OPFS の中身から返す。`/system` は保存済み目録の SHA-256 で検証し、`/user` の重ね合わせと設定アプリの例外も適用する（パスと応答の形は案）。詳しくは [lifecycle.md](lifecycle.md#service-worker決定) を参照

## 復旧画面（決定 2026-11-01）

- カーネルだけで描く最低限の画面
- できること: `/user` の変更を消す、`/system` を取り直す、全部消す
- 起動に失敗したら自動で出す。URL に `?recovery` を付けても出せる（名前は案）

## ebina-front との関係（決定 2026-11-01）

ebina-front は同じカーネルを配り、目録の取得元を自分（GitHub Pages）に向けるだけにします。

## 未決のこと

- ファイルの木に舞台の名前を付けるか（例 Loge〈楽屋〉、Magasin〈道具倉庫〉）。付けないなら「ファイルの木」のまま
- 目録の形、パスの名前、ファイル名（上記の実装は案）
- ファイルの木の API（関数名と形）
- 今の `.binapp`・`bundled/`・`binette:system` / `binette:bundled` の入手元を、この形にどう移すか
- 開発用の配布方法（今の実装は案）
- `regie-worker.js` の中身を毎回は確かめていない。必要になったら、`regie.js` にそのハッシュを埋め込み、取ってから確かめる案

同梱の Filer は `system/boot.json` の `roles.files` に設定されます。
