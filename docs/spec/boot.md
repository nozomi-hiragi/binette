# 起動と配布

[仕様の目次](README.md)

Binette を「カーネルだけ配り、残りは取ってきてブラウザの中に置いて動かす」形にするための仕様です。目的は、アプリの上でアプリを作れること、ホームバーのような OS の部品もアプリの上でいじれることです（のぞみ 2026-11-01）。

> [!NOTE]
> 2026-11-01 に決めた構成です。目録とファイルの木からの起動は実装済みです。カーネルの分離配布、Service Worker、役割 API とシェルはこれから実装します。ファイル名・パス・関数名は、どれも **案** です。役割と API の受け渡しは [roles.md](roles.md) にあります。

## 方針（決定 2026-11-01）

- カーネルは 1 つか数個のファイルにして配る
- ほかの部品（シェル、システムアプリ、AS のコンパイラなど）は HTTP で取ってきて、ブラウザの中のファイルの木に置いて動かす
- 配布元から取る、変えない側のもの（固定物）は、WASM か minify した JS にして、ハッシュで改変を検知する
- カーネルは、まず TS（今の Régie の延長）で作る。形が固まってから、中身を Rust（ビルド済みの WASM）に移すかを決める。アプリの上で編集してビルドし直すもの（シェルやアプリ）は、ブラウザで動く asc を使うので AS のまま

## 層（決定 2026-11-01）

| 層 | 中身 | 変えられるか |
| --- | --- | --- |
| 入口 | `index.html`、Service Worker | 変えられない |
| カーネル | Régie と Scene。起動、取得、検査、ファイルの木、Worker ＋ WASM の実行、ライフサイクル、スタック、役割の割り当て、権限、アプリの UI の描画、シェルが落ち続けたときの最低限の大枠、Apps、復旧画面 | 変えられない |
| ファイルの木 | パス → 中身。`/system` の上に `/user` を重ねて見せる | 権限のあるアプリだけ |
| ユーザー空間 | シェル（ホームバー・通知などの大枠）、ホーム、設定、デザイナー、ふつうのアプリ。どれも役割を持つかどうかだけが違う、ふつうのアプリ（[roles.md](roles.md)） | 設定アプリ以外は差し替えられる |

- Scene はアプリの UI を DOM に描くので、メインスレッドで動く。取ってきたコードをメインスレッドで動かさないため、Scene はカーネルに入れる
- アプリ（システムの部品を含む）は、どれも Worker の中の WASM で動き、DOM には触れない

## 配るファイル（案）

| ファイル | 仕事 |
| --- | --- |
| `index.html` | 入口。`regie.js` を SRI（`integrity` 属性）付きで読む |
| `regie.js` | カーネル本体。minify した JS |
| `regie-worker.js` | アプリを動かす Worker の中身 |
| `sw.js` | Service Worker。入口とカーネルをキャッシュし、ファイルの木を URL で返す |

- カーネルは `regie.js` と `regie-worker.js` の 2 つにする（決定）。Worker の中身は別ファイルにする（今の Blob URL の Worker をやめる。CSP の `worker-src blob:` も要らなくなる）
- AS のコンパイラ（asc）はカーネルに入れない（決定）。重い（約 13.6 MB、gzip で約 2.9 MB）ので、ファイルの木から取る部品にする

## 取ってくるファイル（案）

| パス | 仕事 |
| --- | --- |
| `manifest.json` | 目録。版と、各ファイルのパス・SHA-256・大きさ |
| `system/boot.json` | 役割の既定の割り当て（どのアプリをシェル・ホーム・設定にするか） |
| `system/apps/<アプリ>/` | システムアプリ（シェル、ホーム、設定など）。`app.json` とビルド済みの `.wasm` |
| `system/bundled/<アプリ>/` | 同梱アプリ。システムアプリと同じファイル形式（案） |
| `system/tools/asc.js` | AS のコンパイラ。minify した JS で、Worker の中で動かす |

## ファイルの木（決定 2026-11-01）

- できることは、パス・読む・書く・一覧・削除・重ね合わせだけ。POSIX のような権限の欄やリンクは持たない
- 保存先は IndexedDB（決定）
- 見え方は、`/system` の上に `/user` を重ねたもの。同じパスなら `/user` が勝つ。`/user` のファイルを消せば元に戻る
- アプリはファイルの木に、辞書の API（[roles.md](roles.md)）でしか触れない。権限のないアプリは読むことも書くこともできない（決定）
- 設定アプリはコアで、`/user` で上書きできない（決定。[roles.md](roles.md#設定アプリ決定)）

| パス（案） | 中身 |
| --- | --- |
| `/system/…` | 配布元から取ったもの。読み取り専用。更新で丸ごと入れ替える |
| `/user/…` | 編集した分だけ |
| `/apps/<id>/…` | インストールしたアプリ。`app.json`、ソース、ビルド結果 |
| `/data/<id>/…` | アプリごとのデータ。将来、Coulisses へのバックアップの対象 |

- `AppStore`・`SystemStore` はファイルの木の上に保存する（API と保存先の細部は案。[regie/store.md](regie/store.md)）。目録とハッシュの検査は実装済み。アプリに渡す権限付き API はまだ実装していない

## 目録と現在の配布（案）

`manifest.json` は `{ "version": "…", "files": [{ "path": "system/boot.json", "sha256": "…", "size": 123 }] }` の形です。SHA-256 は小文字の 16 進、サイズはバイト数です。版はファイル一覧の JSON の SHA-256 で、内容が変わると変わります。保存した目録は `/system/.manifest.json` に置き、固定物と一緒に入れ替えます。

`system/boot.json` は `roles.home`・`roles.settings` に既定アプリの ID を入れます。`system/apps/<フォルダ>/` と `system/bundled/<フォルダ>/` に `app.json`、`app.wasm`、`index.html`、必要な `icon.svg` を置きます。同梱アプリの配置と入手元は案です。シェルとその役割は後の PR で追加します。

## アプリの置き方（決定 2026-11-01）

- インストールしたアプリは、ソース（`app.json`、`.ts`、`.css`）をそのまま置き、ブラウザでビルドして、結果を同じ所に残す。アプリの上でアプリを作るときと同じ道にする
- ビルドは Worker の中の asc で行う
- システムアプリは固定物なので、ビルド済みの `.wasm` を取ってきて置く。ブラウザではビルドし直さない

## 起動の流れ（決定 2026-11-01）

1. `index.html` が `regie.js` を読む。改ざんはブラウザが SRI で検知する
2. カーネルがファイルの木を開く
3. 目録を取り、手元の `/system` と比べて、足りないファイルや新しいファイルを取る
4. 取ったファイルの SHA-256 を目録と比べ、合っていれば `/system` に置く
5. `boot.json` と設定から役割の割り当てを決め、カーネルはシェルだけを起動する。シェルが大枠とアプリの表示領域を描き、その中でホームを呼ぶ（[roles.md](roles.md)）
6. `/system` のファイルは、読み込むたびにもハッシュを確かめてから動かす
7. どこかで失敗したら、カーネルだけで描く復旧画面を出す

初回は、既定のアプリを割り当て済みで出します（決定）。

## 更新（決定 2026-11-01）

- 起動ごとに目録だけを確かめる。新しい版があれば知らせ、設定アプリで「更新」を押したら `/system` を入れ替える
- 取得元は、今は同じオリジンだけ。ほかの取得元（GitHub など）は後で考える
- 現在は更新があると起動画面に知らせ、復旧画面の取り直しでも更新できる。設定アプリの更新 API は後の PR で追加する
- 起動時に配布元の目録を取得できなければ、保存済みの `/system/.manifest.json` と、そこに載る固定物の大きさ・SHA-256 を検証して起動する。この場合は更新通知を出さない。保存目録がない、または検証に失敗した場合は復旧画面にする
- 取得できた目録の形式や取得元の検査失敗、保存目録と同じ版なのに内容が違う場合は、保存済みへの切り替えで握りつぶさず復旧画面にする

## 改変の検知（決定 2026-11-01）

- カーネル: `index.html` の SRI でブラウザが確かめる（カーネルは自分のハッシュを自分では確かめられないため）
- `/system` のファイル: 目録の SHA-256 と、取ったときと読み込むたびの両方で比べる。IndexedDB の中身を書き換えられても気づける
- 目録: 今は HTTPS と同じオリジンを信じる。取得元を増やすときに、署名とカーネルに埋め込む公開鍵を足す
- 現在の保存目録は署名がない。オフライン時や更新待ちの旧版など、同じ版の配布元目録と照合できない場合は、保存目録と固定物の両方を同時に改変されると検知できない。旧版の目録の信頼方法は未決
- `/user` と `/apps` のファイルはハッシュで見ない。書けるのは権限のあるアプリだけなので、権限で守る

## Service Worker（決定 2026-11-01）

- 入口とカーネルをキャッシュし、オフラインでも起動できるようにする
- ファイルの木を URL として返す（例 `./fs/system/…`、パスは案）。画像や CSS などがふつうの URL で読め、相対パスもそのまま使える
- 今の Service Worker（[lifecycle.md](lifecycle.md#service-worker決定)）の役割は、この形に置き換える（案）

## 復旧画面（決定 2026-11-01）

- カーネルだけで描く最低限の画面
- できること: `/user` の変更を消す、`/system` を取り直す、全部消す
- 起動に失敗したら自動で出す。URL に `?recovery` を付けても出せる（名前は案）

## ebina-front との関係（決定 2026-11-01）

ebina-front は同じカーネルを配り、目録の取得元を自分（GitHub Pages）に向けるだけにします。

- 目録の形、パスの名前、ファイル名（上記の実装は案）
- ファイルの木の API（関数名と形）
