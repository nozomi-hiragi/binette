# ストレージ

[仕様の目次](README.md)

> [!NOTE]
> 2026-11-03 にのぞみが決めた構成です（この節の中身はすべて決定）。実装の入口は [regie/store.md](regie/store.md) にあります。アプリに渡す API は従来の `storage` を使います。

Binette の保存の一番下の層です。持ち主ごとのフォルダに読み書きするだけで、その上のPigeon（伝書鳩、[pigeon.md](pigeon.md)）とアプリ間のファイル共有のことは知りません。

```
┌──────────────────────────────────────────┐
│ アプリ間のファイル共有  共有フォルダ・共有 ID・権限 │
├──────────────────────────────────────────┤
│ Pigeon（伝書鳩）       手紙・受信欄・通知          │
├──────────────────────────────────────────┤
│ ストレージ             OPFS の中身＋IndexedDB の表 │  ← この仕様
└──────────────────────────────────────────┘
```

## 方針

- ファイルの中身は OPFS（Origin Private File System）に、メタデータは IndexedDB に置く
- OPFS の中に、カーネルとアプリの単位でフォルダを作る。`プロバイダー/アプリ` の 2 重のフォルダにする
- フォルダの中に実ファイルを平らに置く。ファイル名はファイルのハッシュ値
- ファイルを置くのと同時に、IndexedDB にパスをキーにしてメタデータ（保存日、更新日時、ファイル名など）を保存する
- 編集・削除・移動はメタデータを書き換えるだけにし、参照されなくなった実ファイルは GC で消す
- アプリが触れるのは、そのアプリのフォルダの中だけ

OPFS だけでは何個かのファイルを「全部書くか、何も書かないか」で書けず、一覧も遅いため、どちらも IndexedDB の表で受け持ちます。IndexedDB だけでは大きいファイルを少しずつ読み書きできないため、中身は OPFS に置きます。

## OPFS のフォルダ

```
OPFS
├─ _0/                       プロバイダー 0（Binette 自身）
│  ├─ provider.json          プロバイダーの情報（名簿の写し）
│  ├─ -0/<sha256>            アプリ 0 のファイル
│  └─ -1/<sha256>
├─ _1/
│  ├─ provider.json
│  └─ -0/<sha256>
└─ shared/<共有 ID>/<sha256>  共有フォルダ（アプリ間のファイル共有の層が使う）
```

- プロバイダーのフォルダとアプリのフォルダは、どちらも 0 からの連番の 16 進（`0x` なし、小文字）にする。番号は名簿で管理し、使い回さない
- プロバイダーのフォルダの先頭には `_`、アプリのフォルダの先頭には `-` を付ける（例 `_0/-0/`、`_1/-a/`）
- ほかのフォルダ名の先頭に `_`・`-` は使わせない。共有フォルダは `shared`
- プロバイダー `_0` は Binette 自身。カーネルの部品と埋め込みのアプリ（`cadre`・`designer` など）を入れる
- サブアプリは親と同じフォルダを使う
- プロバイダーのフォルダの直下には、情報用の `provider.json` を置いてよい。正は IndexedDB の名簿で、`provider.json` は人や復旧のための写し。食い違ったら名簿に合わせて書き直す

### 実ファイル

- ファイル名は中身の SHA-256 の 16 進（小文字 64 文字）。提供リストの `integrity` と同じハッシュなので、インストール時の検査と保存を兼ねる
- 同じ持ち主の中で、同じ中身は 1 つだけ置く
- 実ファイルは書いたあとに変えない。変えるときは別のハッシュの新しいファイルになる

## IndexedDB の表

```
providers  キー 番号 → { url, name, added }
apps       キー [プロバイダー番号, 番号] → 完全なアプリ ID
files      キー [持ち主, パス] → { hash, history, deleted?, name, size, created, modified }
```

- `providers` と `apps` が名簿。完全なアプリ ID（[app-id.md](app-id.md)）は URL や `.` を含むので、フォルダ名には番号を使い、ID との対応をこの名簿で持つ
- `shared/<共有 ID>` も通常の持ち主と同じハッシュ方式で保存し、共有の名簿と権限は共有の層が管理します。
- `files` の持ち主は `_<プロバイダー番号>/-<アプリ番号>` か `shared/<共有 ID>`。パスはその中の論理パス（例 `/data/notes/memo.txt`）
- `hash` は今の中身の実ファイル名。`history` は古いハッシュの新しい順のリストで、10 個まで
- `deleted` は消した日時。付いている間は一覧に出さない
- 日時は Unix epoch ミリ秒

### アプリのフォルダの中身

アプリのフォルダには、ビルド結果・ソース・アプリのデータを入れ、表のパスで分けます。

| パス | 中身 | アプリから |
| --- | --- | --- |
| `/build/…` | ビルド結果（WASM、HTML） | 触れない |
| `/source/…` | `app.json`、ソース、アイコン | 触れない |
| `/data/…` | アプリのデータ | 読み書きできる |

### カーネルの層

今の `/system` と `/user` の重ね合わせは、プロバイダー `_0` の表の中で `system`・`user` の 2 つの層として持ちます。見え方は今と同じで、同じパスなら `user` が勝ち、`user` の行を消せば元に戻ります。設定を含む `cadre` パッケージを `user` で上書きできないのも今と同じです（[boot.md](boot.md#ファイルの木決定-2026-11-01)）。

## 書き方

- **書く**：中身を OPFS に書く → `files` の行を 1 回のトランザクションで書き換える。表を書く前に落ちても表は古いままなので、古い中身と新しい中身が混ざらない
- **編集**：編集後の中身をそのハッシュの名前で置き、`hash` を付け替え、古いハッシュを `history` の先頭に入れる
- **削除**：`deleted` を付けるだけ。復元はそれを外すだけ
- **移動・名前の変更**：表を書き換えるだけ
- **何個かまとめて**：中身を全部置いてから、`files` の行をまとめて 1 回のトランザクションで書き換える
- **OS の更新**：新しい中身を全部置いてから、`_0` の `system` 層の行を 1 回で入れ替える。古い版は履歴に残るので、戻すのも表の書き換えで済む。目録の SHA-256 の検査は今と同じ（[boot.md](boot.md#改変の検知決定-2026-11-01)）

## GC

- どの行の `hash`・`history` からも指されていない実ファイルを消す
- `deleted` を付けてから 30 日たった行を消す
- 1 日 1 回動かす（スケジューラの OS の予定 `os/gc`、[scheduler.md](scheduler.md#os-の予定)）
- アプリを消したら、名簿と表からそのアプリを外し、フォルダは同じ GC の決まりで消える。ユーザーが明示的に消したければ、その場で消せる
- 中身を置いたあと表を書く前に落ちたときに残る実ファイルも、GC で消える

## 提供リストの移転

提供リストの `movedTo`（[app-id.md](app-id.md)）で URL が変わったときは、`providers` の `url` を書き換えるだけにします。フォルダは動かしません。
