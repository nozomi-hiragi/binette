[仕様の目次](README.md)

> [!NOTE]
> 2026-11-02 にのぞみが決めた構成です（この節の中身はすべて決定）。一部を実装しています。今のコードの形は [今のコードとの差](#今のコードとの差) にあります。App URL（`/<ID>`）とリストの署名は、この仕様では決めません（[あとで足すもの](#あとで足すもの)）。アプリ管理（登録・インストール・更新・削除の操作と画面）は [app-manager.md](app-manager.md) にあります。

## 方針

- アプリは **提供リスト** から入れる。提供者が自分の提供アプリの一覧（提供リスト）を公開し、ユーザーはその URL を登録する。登録したリストのアプリが、ストアのような所に並び、そこから入れる
- アプリの完全な ID は **提供リストの URL ＋ `#` ＋ 識別子**。ID そのものが正しい URL になる
- 提供リストのページは HTML
- Cadre（ユーザー向けの呼び名は「枠アプリ」、英語 frame app）は独立したアプリ。ホームと設定は Cadre の **サブアプリ**
- サブアプリの ID は、親の識別子に `.` でサブアプリの識別子を連結したもの

## 完全な ID

```
https://nozomi-hiragi.github.io/apps/#memo
└──────── 提供リストの URL ────────┘ └ 識別子
```

- ID は URL として正しい形にする。開けば提供リストのページが返り、ブラウザは `id="memo"` の要素まで移動する
- フラグメント（`#` のあと）は「提供リストの中の、その識別子の項目」を指す。JSON にはフラグメントの標準の意味が無いので、Binette がこの意味を決める
- 同じ識別子でも、リストの URL が違えば別のアプリ。同じアプリが 2 つのリストに載っていれば、別のアプリとして扱う

### 識別子

- Web の URL で使える文字なら何でもよい。英数字やよく使う記号以外は、% エンコードした状態で扱う
- `.` はサブアプリの区切りなので、識別子には使えない
- 比べるのは % エンコードしたあとの文字列。`%e3` のような 16 進は大文字（`%E3`）に揃える。英字の大文字と小文字は区別する（`Memo` と `memo` は別）

### 提供リストの URL

- `https:` だけ。`http:` は、設定のデバッグメニューで有効にしたときだけ使える（開発用）
  - https で配った Binette からは、ブラウザの混在コンテンツの制限で、`http://localhost`・`127.0.0.1` 以外の http は取れない
- クエリ（`?`）やフラグメント（`#`）を持つリストの URL は誤り
- `new URL()` で読み、正規化（ホストの小文字化、既定のポートの省略など）はブラウザの規則に任せる。比べるのは正規化したあとの文字列
- localhost などの開発中の配信元に、ほかの特別な扱いは無い。デバッグで http を有効にすれば、普通のリストとして使える

### 埋め込みのアプリの ID

ID は、アプリをどう入れたかで分けます。

- **提供リストから入れたアプリ**: URL の ID（リストの URL ＋ `#` ＋ 識別子）
- **OS に埋め込んで配るアプリ**: 生の識別子をそのまま ID にする（例 `cadre`、サブアプリは `cadre.home`）

- 生の ID は `:` を含まない。URL の ID は必ずスキーム（`https:`）を含むので衝突せず、提供リストのアプリが生の ID を名乗ることもできない
- 埋め込みのアプリは OS と一緒に配られ、OS の更新（ソフトウェア・アップデート）で新しくなる。リストからは更新しない
- 生の ID は OS の版や配信の URL に左右されないので、OS を更新しても保存データはそのまま残る
- 同じアプリを、ある OS は埋め込み、別の OS はリストから入れることもできる。その 2 つは別の ID なので、別のアプリとして扱う

## 提供リスト

提供リストは HTML のページです。人がブラウザで開いて読め、OS は中の機械向けのリスト（JSON）を読みます。

### 機械向けのリストの置き方

1. `<link rel="binette-apps" href="apps.json">` で JSON を指す（PWA の `<link rel="manifest">` と同じ形）
2. HTML に埋め込む: `<script type="application/json" id="binette-apps">…</script>`。この種類の script は実行されない

- OS はまず 1 の link を探し、無いときだけ 2 を読む
- link があれば link だけを使う。link の JSON が取れない・読めないときも、埋め込みには切り替えずに誤りにする
- どちらも無いページは「Binette の提供リストではありません」
- link の `href` は HTML の URL を基準に、JSON の中の相対 URL は JSON の URL を基準に解決する。埋め込みの JSON は HTML の URL を基準にする
- HTML は DOMParser で読むだけで、スクリプトは動かさない
- 別のオリジンから GET するので、配信元が CORS を許す必要がある（GitHub Pages は許している）
- HTML の各アプリの要素に `id="<識別子>"` を付けると、ID を開いたときにその項目まで移動する（付けるかは提供者の自由）

### JSON の形

```json
{
  "name": "のぞみのアプリ",
  "apps": [
    {
      "id": "memo",
      "source": "https://raw.githubusercontent.com/nozomi-hiragi/memo/0123abcd/",
      "version": "1.2.0+0123abcd",
      "integrity": { "/": "sha256-…" },
      "requires": { "app": "0.1", "storage": "0.1", "ui": "0.1" }
    }
  ]
}
```

| 欄 | 必須 | 説明 |
| --- | --- | --- |
| `name` | 必須 | リストの表示名 |
| `apps` | 必須 | アプリの配列 |
| `apps[].id` | 必須 | 識別子。アプリの `app.json` の `id` と一致しなければインストールで止める |
| `apps[].source` | 必須 | アプリ本体（`app.json` を置いたフォルダ）の URL。リストとは別の場所でよい |
| `apps[].version` | 必須 | 版の文字列 |
| `apps[].requires` | 任意 | 必要なホスト ABI。機能名から版への辞書（例 `{ "storage": "0.1" }`）。キーは `[a-z][a-z0-9-]*`、値は `0.N` または 1 以上の `N` の文字列。配列・null・範囲指定・パッチ版は不可。未知の機能も形式が合えば読み、OS との照合で非対応とする |
| `apps[].integrity` | 任意 | 改ざん検出のハッシュの辞書（[下](#ハッシュ)） |
| `apps[].name`・`icon`・`description` | 任意 | 表示用（[app-manager.md](app-manager.md#カタログの表示用の欄)） |
| `movedTo` | 任意 | 引っ越し先のリストの URL（[下](#引っ越し)）。これがあるリストは `apps` を読まない |

- `requires` は省略でき、空の辞書も有効。未記載の従来アプリは今までどおり取得・ビルド後に WASM を検査する
- カタログ生成では実際にビルドした WASM の `binette:<機能>@<版>` import から作り、`env` を除き、機能名順で書く。ソースの import 文や SDK の公開機能一覧から推測しない。同じ機能の複数版や形式外の module は生成を止める
- OS は自分の `HOST_ABI` の module と完全一致で照合する。非対応ならアプリのファイルを取る前に `unsupported_abi` で止める。`requires` は事前の案内であり、ビルド後と起動前の WASM 検査も続ける

### 更新

- 更新は、そのアプリを入れたリストからだけ届く
- OS はリストの `version` を文字列として見て、入っている版と **違ったら** 更新がある。前後は判定しない（下げた版も届く）。いつ入れるか（自動更新、権限が増える更新）は [app-manager.md](app-manager.md#更新)
- 中身を固定したい提供者は、`source` に commit 入りの URL を書く。版に `+0123abcd` のようなビルドメタデータ（semver の書き方）を付けると、同じ版のまま commit だけ変えても更新が届く。OS は `+` のあとを特別扱いせず、版文字列の一部として比較する

### ハッシュ

- 各アプリの `integrity` は任意の辞書。キーは `source` から見たパス、値は `sha256-<base64>`（Web の SRI と同じ書き方）
  - `"/"` はアプリ全体、`"src/"` のように `/` で終わるキーはフォルダ、それ以外はファイル
  - 例: `{ "/": "sha256-…" }`、`{ "src/": "sha256-…", "app.json": "sha256-…" }`
- 書いた分だけ OS が確かめ、合わなければインストール（更新）を止める
- `/` は、インストール・更新のため OS が取得したすべてのファイルを対象にする。`app.json`、入口の CSS と AS およびその import、アプリとサブアプリのアイコンなどが含まれる。明示したファイルキーを検証するために取得したファイルも含む
- フォルダキーは、OS が取得したそのフォルダ配下のファイルを対象にする。HTTP では配下の全ファイルを列挙できない
- `/` とフォルダのハッシュは、対象ファイルをそのフォルダからの相対パス（`/` では `source` からの相対パス）の UTF-16 コード単位順に並べ、各ファイルについて `UTF-8(パス) 0x00 UTF-8(バイト数の10進表記) 0x00 中身` を連結したバイト列の SHA-256。Régie の CLI で計算できる

### 引っ越し

- リストを別の URL に移したときは、古い URL のリストに `"movedTo": "新しい URL"` を書く
- OS は古いリストの `movedTo` を見つけたら、登録を新しい URL に付け替え、そのリストから入れたアプリの ID も新しい URL に付け替える。保存データ・許可した権限・役割の割り当ても引き継ぐ
- 古いリストを書き換えられるのは、その配信元を持つ本人だけなので、ほかの人が引き継ぎを起こすことはできない

### 既定の提供リスト

- OS（カーネル）を配る人が、カーネル側の管理領域の `system/boot.json` に `"lists": [URL, …]` として書く
- 既定のリストは、ユーザーが消すことも変えることもできない
- ユーザーが自分で足したリストは、これとは別に持つ

## Cadre・ホーム・設定

- Cadre は独立したアプリ。ユーザー向けの呼び名は「枠アプリ」（英語 frame app）。役割名 `cadre` は変えない
- ホームと設定は Cadre のサブアプリ（埋め込みなら `cadre.home`・`cadre.settings`）
- ホームと Cadre は差し替えられる（[roles.md](roles.md)）。ほかの提供者が、ホームだけのアプリや別の Cadre を配ってもよい
- 役割の割り当ては役割ごとに独立している（`system/boot.json` の既定と設定の `roles`）。`cadre` を差し替えても `settings` は既定の Cadre の設定のまま変わらない。設定アプリはコアで差し替えられない（2026-11-01 の決定のまま）

### 配り方

- 既定の Cadre は、OS に埋め込んでも（生の ID）、初回の起動でリストから取ってきても（URL の ID）よい。どちらにするかは OS を配る人が決める
- Binette は既定の Cadre を埋め込む。ID は `cadre`・`cadre.home`・`cadre.settings` で、OS の更新で新しくなり、復旧画面（`?recovery`）で OS のものに戻せる
- 普通のアプリ（designer など）は埋め込まない。既定のリストに載せ、アプリ管理（[app-manager.md](app-manager.md)）からインストールできるようにする
- Binette の既定のリストは、固定 URL `https://nozomi-hiragi.github.io/binette-apps/` だけにする。OS のブランチが違っても、同じリストのアプリは同じ ID になる

## サブアプリ

サブアプリは、親のアプリに完全に埋め込まれた、ユーザー側への「口」です（Android で 1 つのアプリがランチャーに複数の入口を出すのに近い）。

- ID は親の識別子 ＋ `.` ＋ サブアプリの識別子。例 `https://nozomi-hiragi.github.io/apps/#memo.widget`、埋め込みなら `cadre.home`。深さは 1 段だけ
- 親の `app.json` の `sub` にサブアプリを並べる。ファイルをどう分けるかは作者が決める
- 親と一緒にインストール・更新・削除される。単独では入れられない
- 保存領域と権限は親と共有する。サブアプリが自分で持つのは名前・アイコン・役割・一覧に出すかだけ
- 入口は親の `entry.as` 1 つ。OS は起動のときに、どのサブアプリとして開いたかを渡す。アプリは `onCreate(last, api)` の `api.sub()` で識別子を取る（親として開いたら空文字列）。中でクラスを分けるか、ファイルを分けて import するかは作者次第
- 親と同時に動くときは、別の Worker・スタックの別の項目にする。同じ Worker で動かす選び方は、必要になったら `app.json` の欄として足す
- ホームの一覧に出すかは、サブアプリごとに作者が `listed` で決める。既定は出す（`true`）

```json
{
  "id": "cadre",
  "name": "Cadre",
  "roles": ["cadre"],
  "entry": { "as": "src/main.ts" },
  "sub": {
    "home": { "name": "ホーム", "icon": "home.svg", "roles": ["home"] },
    "settings": { "name": "設定", "icon": "settings.svg", "roles": ["settings"] }
  }
}
```

| `sub` の各値の欄 | 必須 | 説明 |
| --- | --- | --- |
| `name` | 必須 | 表示名 |
| `icon` | 任意 | アイコンのパス（`app.json` の場所から） |
| `roles` | 任意 | 名乗る役割 |
| `listed` | 任意 | ホームの一覧に出すか。既定は `true` |

## 表示

- アプリの出どころは、リストの `name` を大きく、リストのホストを小さく添えて出す（例「のぞみのアプリ · メモ」と `nozomi-hiragi.github.io`）。リストの `name` は誰でも名乗れるので、ホストで偽物に気づけるようにする
- 詳細画面では完全な ID（URL）も見せる

## あとで足すもの

- **署名付き ID**（任意）: アプリの基本の ID は URL の ID のまま。提供者は、URL の ID に署名（提供者の鍵 ＋ 識別子）を結びつけた「URL の ID：署名」の組を、あとから出したり消したりできる。同じ署名を結びつけたアプリは、別の口（別の URL や埋め込み）から入れても同じアプリとしてデータを共有する。正しさは URL の保持者が決める（URL の保持者が正義）
  - 鍵を取られたら、正しい URL で改めて署名を結びつけ直し、それを正とする
  - URL を捨てるときは、提供者が破棄リストに載せる。破棄し損ねたドメインを他人に取られて配られた場合は、提供者の責任とする
  - 鍵は提供者の手元で持つ
  - URL の ID の付け替え: `URL の ID` → `URL の ID：署名` → `新しい URL の ID：署名` → `新しい URL の ID：新しい署名` のように、1 回に URL か鍵の片方だけを変える段を踏めば、アプリの URL の ID を変えられる。段を見逃して追えなくなったユーザーは切り捨てる
  - 鍵だけを頼りに URL を変える段では、古い URL がまだ取れるなら、その宣言（`movedTo`・破棄リスト）と食い違わないことを確かめる。食い違えば古い URL を正とする
- App URL（`/<ID>`）
- **`source` の署名**（任意）: 鍵がある場合、アプリ ID と `source` の URL の組に署名して、公認の置き場所であることを示せる。`source` は位置を知らせるものなので、版（commit）は入れない。鍵の形式、公開鍵の置き場所、署名するバイト列の形は未定

## 今のコードとの差

今のコードでは、Régie は完全なアプリ ID を保存・役割の割り当て・起動履歴に使い、`sub` の各入口と `api.sub()` に対応しています。サブアプリは親と保存領域と権限を共有し、別の Worker で動きます。

- 入手元はシステムアプリが `binette:system`、同梱アプリが `binette:bundled`（[apps/](apps/README.md)）。Cadre は `apps/cadre` の 1 つのパッケージで、ホーム・設定はその `sub`。ID は `cadre`・`cadre.home`・`cadre.settings`。Filer は同梱のまま、ID は `filer`。デザイナーは binette-apps の提供リストから入れ、完全な ID は `https://nozomi-hiragi.github.io/binette-apps/#designer`。従来の Binette のリストとは ID が変わるため、保存データは引き継がない。`app.json` の `id` は既定で識別子の規則（`.` を含まない）で検査し、旧 ID の暫定例外は使わない
- `system/boot.json` は `roles` に上の埋め込み ID を持ち、`lists: []` を出力する。Régie は既定とユーザー登録の提供リスト、インストール・更新・移転に対応する。提供リストのページとアプリ管理（[app-manager.md](app-manager.md)）はまだ無い
- `@binette/core` に識別子・提供リストの URL・完全な ID の正規化と組み立て、提供リストの読み取り、`app.json` の `sub` の検査、`integrity` の計算と検証の関数がある。Régie は取得したファイルを使って `/` を含む `integrity` を検証し、CLI には `integrity` コマンドがある。CLI で `/` またはフォルダキーを計算するときは、実際にビルドして取得ファイルを確定するため、`--replique <packages/replique>` が必要。ファイルキーだけを指定するときは、各ファイルを直接読む
