# アプリ管理

[仕様の目次](README.md)

> [!NOTE]
> 2026-11-09 にのぞみが決めた構成です（この節の中身はすべて決定）。Régie の TS API（`system.lists`）、カタログの表示用の欄、アプリに渡す `manager`（Réplique の `AppManagerApi`）、画面 `cadre.apps`、OS の権限のダイアログ、既定の提供リスト（`deno task pages` が作る。アプリは `catalog/`）は実装済みです。カタログのアイコンは、OS（Régie の `system.lists.icon(url)`）が提供リストの取得と同じ決まり（https、制限時間）で 1 回だけ取り、SVG と PNG・JPEG・GIF・WebP（64 KiB まで）を data URL にして写しの `icon` に入れます。届くまでと取れないときは名前の頭文字で代えます。提供リストと ID の決まりは [app-id.md](app-id.md) にあります。

提供リスト（操作の名前では repo）の登録、アプリのインストール・更新・削除、アプリのデータの管理を受け持つ、アプリ管理の仕様です。

## 方針

- 提供リストはカタログ。アプリの場所（`source`）を知らせるだけで、アプリのコードはどこに置いてもよい
- 操作口（API）は、役割 `apps-manager` に割り当てたアプリにだけ届く
- 画面は Cadre のサブアプリ `cadre.apps`（表示名「アプリ」）が持つ。設定と同じく差し替えられない
- 権限の確認は OS（カーネル）がダイアログで出す。アプリ管理のアプリが描くものではない
- アプリのデータはアプリ管理が受け持つ。データを消せるのはアプリ管理だけ

## カタログの表示用の欄

提供リストの JSON の各アプリに、表示用の欄を任意で書けます（[app-id.md](app-id.md#json-の形)）。

| 欄 | 必須 | 説明 |
| --- | --- | --- |
| `apps[].name` | 任意 | 表示名 |
| `apps[].icon` | 任意 | アイコンの URL（JSON の URL を基準に解決する） |
| `apps[].description` | 任意 | 短い説明 |

- 無ければ、一覧には識別子を出す
- インストールしたあとは、アプリの `app.json` のもの（`name`・`icon`）を正とする

## ABI の互換性（決定）

- 提供リストの `requires`（[app-id.md](app-id.md#json-の形)）を、現在の OS の `HOST_ABI` と照合する。機能と版が一致しなければ「この OS では使えません（storage 0.3）」のように理由を出す。複数あれば機能名順に読点で並べる
- `AppManagerApi.compatible(id)` と `compatibilityError(id)` で事前の判定と理由を読む。`requires` の省略・空辞書は事前の制限なしとし、従来どおりビルド後の WASM 検査を行う。権限を認める判定とは別で、既存の OS call・権限判定は変えない
- 「探す」の行と詳細に理由を小さく出し、詳細の「入れる」「更新」「適用」は押せなくする。詳細を開く行は押せる。インストール処理も UI に頼らず、キャッシュした要求が非対応ならリストの再取得より前に、最新リストで非対応と分かったときは本体の取得より前に `unsupported_abi` で止める。自動更新も同じ
- 保存済み WASM の ABI が合わないときは、`installedError(id)` が「この OS では動きません。入れ直してください」を返す。「入っている」の行と詳細に出し、カタログにあるアプリの詳細には「入れ直す」を出す
- `reinstall(id)` は既存の「本体だけ消す（`uninstall(id, false)`）→ 同じ ID を入れる（`install`）」を順番に行い、データを残す。権限の確認も既存のインストールの手順を使う。途中で失敗・中止した場合もデータは残り、「データだけ」から再試行できる。現在のカタログも非対応なら入れ直しは押せない
- アプリの行は中立の ghost ボタンで、行の背景と文字色を明示する。状態の pill も色を指定し、汎用ボタンの白文字を引き継がない

## 届け先

- 役割 `apps-manager` を名乗り、かつ割り当てられたアプリにだけ、辞書のキー `manager` の API が届く（[roles.md](roles.md)）
- 割り当ては設定と同じく固定。Binette では `cadre.apps`（入手元 `binette:system`）だけ
- 操作は、提供リストの URL とアプリの完全な ID で指す。一覧は番号で数えるが、取得やインストールの途中で一覧が変わっても、別のものを操作しない

## 操作

```ts
const manager = AppManagerApi.from(api); // 取れなければ null
```

| 種類 | 操作 |
| --- | --- |
| 提供リスト | 登録 `addRepo(url)`、登録済みの一覧（URL・`name`・ホスト・消せるか）、削除 `removeRepo(url)` |
| アプリの一覧 | 取れるアプリ（全リスト・リストごと）。名前・アイコン・説明・版・状態 |
| 詳細 | `details(id)`。アプリの `app.json` を取り、名前・版・出どころ（リストの `name` とホスト）・完全な ID・説明・役割・権限と理由・`integrity` の有無と、更新の情報（新しい版、増える権限、準備済みか）を返す |
| インストール | `install(id)`。入っていれば更新を入れる |
| インストール済み | 一覧（本体あり、本体なし・データありの両方）、版、出どころ |
| 削除 | `uninstall(id, withData)`。本体だけか、データごとかを選ぶ。本体なし・データありのアプリのデータを消すのも同じ操作 |
| 更新の確認 | 全リスト `checkUpdates()`、リストごと `checkUpdates(url)`。更新があるアプリの一覧（全リスト・リストごと） |
| 自動更新 | アプリごと・リストごと・全リストのトグル |
| 進捗 | アプリごとの状態と、取ったファイル数・バイト数 |
| 中止 | `cancel(id)` |

- 消せる提供リストかは、保存の位置で決まる。カーネル側の `system/boot.json` にある既定のリストは消せない。ユーザーが登録したもの（ユーザーの領域）は消せる
- 入れたあとにアプリを開く操作は持たない（開くのはホーム）

### 時間のかかる操作

- `install`・`checkUpdates`・`details` などはすぐ戻る。状態が変わったら、OS がアプリの `build()` をやり直させる
- 状態: 待ち・取得・ビルド・保存中（中止できない）・準備済み（更新を適用待ち）・失敗（理由つき）
- 進捗は段階と、取ったファイル数・バイト数で表す。ソースは import をたどって取るので、全体の大きさは先に分からない（割合は出さない）
- 複数のインストール・更新は並列で進める。並列にするのは取得とビルドで、本数は変数で持つ（既定 2。ユーザーが変えられるかは未定）。最後の保存と登録の書き換えは 1 つずつ
- 中止すると、取得・ビルドをすぐやめて、取ったものを消す。止めると都合の悪い最後の処理（保存）は、中止を受け付けなくしてから始める

## 権限の確認

- インストールと、権限が増える更新では、OS がダイアログで確認する。アプリ名・出どころ・権限と理由（更新では増える権限を強調）・「許可して入れる」「やめる」
- ダイアログはカーネル（Scene）が画面の上に直接出す。アプリ管理のアプリは確認を飛ばせない

## 更新

- 更新は、そのアプリを入れたリストからだけ届く。版の比べ方は [app-id.md](app-id.md#更新)
- 自動更新はアプリごとのトグル。リストごとのトグルをオンにすると、そのリストのアプリは個別の設定を残したまま、自動更新をオンとして扱う。全リストのトグルも同じく、すべてのアプリを上書きする
- 既定: アプリごとはオン、リストごとと全リストはオフ（個別の設定に任せる）
- 権限が増える更新は、自動では入れない。更新があることだけを示し、ユーザーが更新を押したときに権限を確認する
- 動いているアプリの自動更新は、更新の準備（取得とビルド）だけをしておく。アプリ管理の画面で「適用」を押すか、アプリが終了したときに適用する
- 手で適用するとき、アプリが動いていれば、OS がアプリを終了させて（onDestroy まで）から適用する
- 適用の途中は、そのアプリを起動させない
- 更新の確認の定期実行はスケジューラに頼む。初期の間隔（30 分）はアプリ管理が送る。スケジューラでは OS の予定 `os/catalogs` になる（[scheduler.md](scheduler.md#os-の予定)）

## 削除

- 消せるのは提供リストから入れたアプリだけ。埋め込みのアプリ（`binette:system`・同梱）は消せない
- 本体だけを消したとき、データは残る。同じ ID を入れ直すと、残ったデータを引き継ぐ
- 本体の無いアプリには、何も実行させない（起動しない、手紙・通知・共有の招待も届かない）
- 本体なし・データありのアプリは、インストール済みの一覧に「データだけ」として出し、アプリ管理からデータを消せる
- ほかのアプリに削除の権限があっても、データは消させない
- 役割に割り当てていたアプリを消したら、その役割は既定にフォールバックする
- 動いているアプリを消すときは、OS が終了させてから消す

## 画面（`cadre.apps`）

Cadre のサブアプリとして `apps/cadre/app.json` の `sub` に宣言します。

```json
{
  "id": "cadre",
  "sub": {
    "apps": { "name": "アプリ", "icon": "apps.svg", "roles": ["apps-manager"] }
  }
}
```

3 つのタブと詳細の画面で作ります。

- **探す**: 提供リストごとの見出し（リストの `name` を大きく、ホストを小さく）。アプリの行にアイコン・名前・説明・版・状態（入れる・入っている・更新あり・進捗）。押すと詳細
- **入っている**: 上に更新の件数、「すべて更新」「更新を確認」と全リストの自動更新のトグル。その下に入っているアプリの行。本体なし・データありのものは薄く出し「データだけ」と添える
- **リスト**: 登録済みの提供リストの行（`name`・ホスト・既定の印）。行ごとに「更新を確認」と自動更新のトグル、消せるものには削除。下に URL の入力欄と「追加」
- **詳細**: 行を押すと同じアプリの中で切り替わり、戻るボタンを持つ。`details(id)` の中身と、そのアプリの自動更新のトグル。ボタンは入れる・更新・適用・中止・削除。進捗も出す
- 削除を押すと、詳細の中に「本体だけ消す」「データごと消す」「やめる」を出す（ダイアログの部品がまだ無いため）

## Binette の既定の提供リスト

- ブランチごとに GitHub Pages に置く（例 `https://nozomi-hiragi.github.io/binette/apps/v0.2.0/`）。そのブランチの `system/boot.json` の `lists` に書く
- OS（`/binette/<ブランチ>/`）の Service Worker の範囲の外に置く。範囲の中だと、ID の URL を開いたときに OS のページが返り、提供リストのページが見えないため（API ドキュメントの `api/<ブランチ>/` と同じ）
- ページ（HTML と `apps.json`）だけを、Docs の workflow で生成する。アプリのコードは写さない
- `source` は commit 入りの raw.githubusercontent.com の URL（例 `https://raw.githubusercontent.com/nozomi-hiragi/binette/<commit>/catalog/designer/`）。raw は 5 分間キャッシュするので、ブランチの URL だと push の直後に `integrity` が合わなくなるため。更新の判定は `version` で行う
- `requires` は同じビルドの WASM imports から自動生成する。`env` は含めず、機能名順で安定させる
- `version` は `app.json` の版 ＋ `+<commit の短いハッシュ>`。`integrity` の `"/"` は CI が Régie の CLI で計算する
- 載せるのは designer とドキュメントアプリ（`docs`）。Filer は役割 `files` の既定なので同梱のまま
