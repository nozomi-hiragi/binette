# アプリ間のファイル共有

[仕様の目次](README.md)

> [!NOTE]
> 2026-11-03 にのぞみが決めた構成です（この節の中身はすべて決定）。共有の作成・招待・承認・退出とファイル操作は実装済みです。Filer とピッカーは今後の作業です。[ストレージ](storage.md) の共有フォルダを、[Pigeon](pigeon.md) の手紙で渡して使います。Filer（ファイル管理アプリ、役割 `files`）はこの上に乗るアプリです。


いちばん上の層です。ストレージの共有フォルダを、Pigeonの手紙で渡して使います。Filer はこの上に乗るアプリです。

## 実装の入口

アプリは辞書の `shares` から共有を操作し、Pigeon の手紙に共有を添付します。操作結果は非同期で受け取ります。詳しい API は [Réplique](replique.md#sharesapi) を参照してください。

## 方針

**共有フォルダ**
- 共有したいときは、`共有フォルダ/個別共有フォルダ` にファイルを置き、個別共有フォルダの識別子をキーにして共有する
- 共有 ID は `crypto.randomUUID()`（UUID v4）で作る。そのまま OPFS のフォルダ名にする
- 共有の識別子のメタデータに権限を書いて、使えるアプリを絞る。権限は `read` と `write`

**招待と承認**
- 共有をPigeonでアプリに投げると、メタデータではそのアプリが「招待中」になる
- 受け手のアプリが承認したら、そのアプリの共有の権限が確定する
- 受け手が承認する前に共有元が共有フォルダを消したら、共有の中身も消える。あとで受け手が受け取ろうとしても「もう無い」になる

**抜ける・消す**
- アプリが共有から抜けても、残っているアプリが引き続き持つ
- 共有を強制的に消したい作成側は、ファイルを削除してから共有から抜ければよい。強い手段なので、あまり使わない想定
- 誰もいなくなった共有は、ストレージの GC の決まりで消える
- アプリを消したときは、そのアプリが共有から抜けたのと同じ扱い

**Filer**
- ユーザーが持つファイルは、Filer の持ち物（Filer のフォルダ）にする
- Filer は、基本的にほかのアプリのファイルには触れない
- アプリがFiler に共有を渡していれば、Filer では「共有/アプリ名」のように見える
- ファイルピッカーの標準アプリはFiler（役割 `files`）。ピッカーで選べるのは、Filer が持つユーザーのファイルだけ
- ピッカーで選んだことを許可とみなす（Android の SAF、Sandstorm の Powerbox と同じ考え方）

**Filer の名簿と共有の状態**
- アプリ側からの共有は、Filer では `共有/アプリ名` として、共有の名簿（`shares` 表）をもとに扱う
- 共有の名簿の内容を、Filer 側の名簿（Filer のフォルダの `files` 表）にうまく書き写す
- 共有のフォルダからFiler自身のフォルダへ移したときは、Filer 側の名簿だけを更新し、実ファイルは共有フォルダに置いたままにする。Filer から見えるそのファイルの状態は「共有 ON」になる
- ピッカーなどでFiler 側から共有を許したときは、実ファイルを共有フォルダに移し、名簿の参照を更新して「共有 ON」と分かるようにする
- Filer で「共有 OFF」にしたら、実ファイルを共有フォルダからFiler のフォルダへ移し、名簿を更新する
- 共有フォルダの名前は `shared`
- ピッカーで渡した共有は、頼んだアプリ自身が受け取るので、招待中を飛ばしてすぐ承認済みにする

```
IndexedDB
├─ shares  キー 共有 ID → { name, created, creator, members: { <アプリ ID>: { access: "read" | "write", state: "invited" | "joined" } } }
└─ files（Filer の持ち物の行）  { name, created, modified, …,  hash } か { …, share: <共有 ID>, path: <共有の中のパス> }
```

- Filer の行が `hash` を持てば、実ファイルはFiler のフォルダにある（共有 OFF）。`share` と `path` を持てば、実ファイルは共有フォルダにある（共有 ON）
- 共有 OFF にすると、その共有からそのファイルが無くなるので、ほかのアプリからは見えなくなる
